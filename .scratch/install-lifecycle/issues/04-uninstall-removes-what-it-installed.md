# 04: Uninstall removes what it installed, and asks what to keep

**Category:** enhancement
**Status:** ready-for-agent
**Blocked by:** 01, 02
**Blocks:** none

**What to build:** Removing the app removes everything it added — daemon, task, `PATH` entry, trusted root,
Caddy data, runtimes, caches, settings, discovery file — and asks two questions before deleting user data:
whether to remove the app's own state, and whether to remove Projects. "Remove everything" leaves nothing behind.

## Evidence

- `NSIS_HOOK_PREUNINSTALL` always calls the non-destructive `agentify uninstall`; `--purge` also deletes
  Projects, so "purge but keep Projects" does not exist.
- `agentify uninstall` aborts when the discovery file is stale (see 01), so today a removed app can leave state,
  trust, and Caddy behind.
- Tauri NSIS hooks cannot add a custom page; two `MessageBox` prompts need no template fork, real checkboxes need one.
- `state.db` has no settings table: Projects, Environments, Resources, tokens, approvals, and audit share it.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** The uninstaller asks two questions — machine-level additions, then the data root — and each answer is honoured exactly, leaving nothing behind when both are yes.

**Settled decisions:**
- Question 1, default yes: remove the daemon, logon task, PATH entry, certificate trust, Caddy data, and caches.
- Question 2, default no: remove the data root — state.db, Project workspaces, runtimes, and Checkpoints.
- Settings, tokens, approvals, and audit live in state.db, so they leave with the data root; no separate settings
  store is invented.
- Two Yes/No prompts, no forked NSIS template.

**Current behavior:**
The uninstaller always runs the non-destructive path and ignores the CLI's exit code. `--purge` removes Projects
too, so there is no way to remove app state while keeping Projects. A stale discovery file makes the CLI abort
before removing anything.

**Desired behavior:**
Uninstall first ensures no daemon or shim from this install is running, then asks the two questions and acts on
the answers. Question 1 removes machine-level additions and caches; question 2 removes the data root. Declining
question 1 is allowed but leaves named leftovers that the report lists; it never strands a running process.
Removal is idempotent, reports each item, and a locked file is reported rather than silently skipped. A "remove
everything" run leaves no data root and no file in the program directory.

**Key interfaces:**
- The uninstall report: per-item outcomes plus the human-readable notes it already carries.
- CLI uninstall flags expressing the two answers independently.
- The installer's pre-uninstall hook: the two prompts, then the composed CLI call.
- Existing seams: the login-item remover, the trust installer, the runtime remover.
- A single declared inventory of install-time effects that both install and uninstall consult.

**Acceptance criteria:**
- [ ] Two prompts appear with the stated defaults, and the answers drive removal.
- [ ] Keeping Projects leaves state.db, workspaces, runtimes, and Checkpoints intact and usable after reinstalling.
- [ ] Removing Projects deletes state.db, workspaces, runtimes, and Checkpoints, and no data root remains.
- [ ] A leftover v0.1.2 logon task is removed even though this build never creates one.
- [ ] A stale discovery file never aborts the uninstall.
- [ ] A running shim or daemon is stopped or named for the user before the program directory is deleted; a locked file is reported.
- [ ] Declining question 1 leaves the named items in place and reports them.
- [ ] The decision matrix — keep/keep, keep/remove, remove/keep, remove/remove — is covered at the uninstall seam.

**Out of scope:**
- Splitting settings out of state.db into a second store.
- A custom NSIS template with checkbox UI.
- Changing the updater.
