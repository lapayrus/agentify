# 01: No build inherits a daemon from another build

**Category:** bug
**Status:** ready-for-agent
**Blocked by:** none
**Blocks:** 04

**What to build:** Starting Agentify must never adopt a daemon it does not ship. A discovery file that names a
dead process is treated as absent; a daemon answering with another build's version is stopped before the caller
starts its own; an install-over or update stops the running daemon before any sidecar file is replaced. A failed
stop is reported, never ignored.

## Evidence

Observed on the v0.1.2 install:

- `%LOCALAPPDATA%\Agentify\discovery.json` names `pid: 6496`, `daemon_version: 0.1.2`, port 62592. Process 6496
  does not exist; `agentify status` exits 1 with "Connection Failed … actively refused". The discovery file
  survives the process it names.
- The shell's `ensure_daemon()` returns early when `discovery.json` exists — no health probe, no build
  comparison — so this file alone prevents the shipped daemon from starting.
- The CLI's `stop_daemon()` errors when the file exists but the daemon does not answer, and `agentify uninstall`
  returns `FAILURE` on that error before removing anything.
- `NSIS_HOOK_PREINSTALL` has no stop step, so an install-over copies over a live `agentifyd.exe`.
- The updater's `shutdown_for` is discarded (`let _ =`), so its failure is silent.
- The `Agentify Daemon` task is `InteractiveToken` with `RestartOnFailure` 3 × 1m; a clean exit or a closed
  window is not a failure, so the task stays down while the file remains.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** A caller trusts a discovery file only when its process is alive, healthy, and the same build, and replaces a live daemon from another build instead of driving it.

**Settled decisions:**
- Takeover is gated. With an Operation in flight, refuse and name the Operation; otherwise ask for graceful
  shutdown, wait a bounded few seconds, then terminate by pid — and only if the image is the daemon binary and
  it has stopped answering.

**Current behavior:**
The existence of the discovery file is treated as proof of a live, compatible daemon. A file left by a crashed
or replaced process blocks the shipped daemon forever, and the stop path treats "file exists, nobody answers"
as a fatal error.

**Desired behavior:**
A discovery file is trusted only when its pid is alive, the liveness route answers, and the reported daemon
version equals the caller's build version. Anything else is a stray daemon: invalidate the file, and if a
process is alive, stop it before starting the shipped daemon. Install-over and update stop the daemon before any
sidecar file is touched and surface a failure. Uninstall treats a stale file as "nothing to stop", removes it,
and continues.

**Key interfaces:**
- Discovery file contents: `pid`, `port`, `url`, `daemon_version`, `api_version`, `created_at`; no new field.
- The daemon's liveness route and the update-readiness route, reused as the in-flight gate.
- The shell's daemon-start path and the CLI's daemon-stop path (also used by the installer).
- The installer's pre-install and pre-uninstall hooks.
- Process termination: verify the image is the daemon binary before killing a pid.

**Acceptance criteria:**
- [ ] A discovery file whose pid is gone produces a fresh daemon on the next launch.
- [ ] A live daemon reporting another build's version is stopped and replaced; no request is served by the old build afterwards.
- [ ] An in-flight Operation blocks the takeover with an actionable message and leaves both processes untouched.
- [ ] Install-over and update stop the daemon before sidecars are replaced, and fail loudly when they cannot.
- [ ] Uninstall succeeds with a stale discovery file and leaves no discovery file behind.
- [ ] Graceful shutdown removes the discovery file; a crash never leaves a trusted one.
- [ ] Tests cover stale file, foreign version, and live matching daemon at the daemon API seam and the shell seam.

**Out of scope:**
- Daemon lifetime, console, and ownership rules (02).
- Uninstaller prompts and the removal inventory (04).
- Changing the version pin table or the handshake payload.
